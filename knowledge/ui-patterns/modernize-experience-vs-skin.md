# Modernize Experience vs Visual Skin

**Status:** Done · **Priority:** High  
**Use when:** Client says “make it modern” on an existing product with a design team.

---

## Split the brief (always)

| Mode | Changes | Success looks like |
|------|---------|-------------------|
| **Skin / UI refresh** | Type, color, spacing, components look | Same flows, clearer/current visual language |
| **Experience modernization** | Steps, IA, defaults, progressive disclosure, errors | Different path through the job; measured behavior change |
| **Both** | Explicit dual scope | Two workstreams, two success metrics |

Saying “modern” without this split causes redesign theater.

---

## Signals it’s experience, not only skin

- Drop-offs mid-flow (analytics/replay)
- Support load on the same tasks
- Workarounds, exports to Excel, shadow processes
- Mobile can’t complete the job (not just “looks cramped”)
- Rules/approvals force cognitive overload

Signals it’s mostly skin: brand lag, inconsistent components, “feels dated,” no behavioral complaint.

---

## Working with an existing design team

1. Name the mode with PM/design lead.  
2. Inventory sacred constraints (compliance, architecture, component library).  
3. Skin → extend tokens/components. Experience → problem framing + options + validation.  
4. Don’t silently expand scope from skin → full IA rewrite.

See: `design-systems/working-inside-existing-ds.md`.

---

## Measurement

- Skin: consistency, a11y, design-system adoption, qualitative “clarity”  
- Experience: task success, time, drop-off, support tickets, activation  

Instrument before large experience bets when possible (same lesson as EY Fabric narrative).
